# 人員可查看畫面：管理設計

狀態：使用者已於 2026-09-11 明確授權實作人員畫面權限，採逐人設定、預覽確認的方案 A。實際人員授權由 admin 自行確認，不在部署時代為分配。

## 本次實作決策

- 舊帳號未設定前維持既有權限，頁面醒目標示「沿用舊制」；首次確認後採白名單。系統建立的新帳號先不開放業務功能。
- 每個畫面群組分查看、操作、匯出／系統列印；共用同一維護流程的合作車行／平台／本店人員合併為通路人員群組，避免共用編輯端點跨類型繞過。
- 報表逐份授權，既有敏感報表資格仍為上限。個人密碼、登出、外觀、說明及可用功能入口不受業務授權限制。
- admin 管理權固定；其他管理者不能編輯、停用或重設 admin，也不能藉由改名取得 admin 身分。已套用白名單者不能經 Django admin 繞過。
- 不做列級／欄位級隔離；開放某畫面即能查看該畫面既有的統計、關聯摘要與下拉選項。獨立原始文件、訂單頁、修改與匯出另驗權限。
- 新增獨立權限模組與 migration；變更以交易、版本檢查、簽署預覽及歷程保護。撤權下一次請求生效。

## 1. 現況與入口

- 現有入口：資料維護區 → 管理者工具 → 帳號與權限，路由 `/system/users/`。
- `sales/views.py:user_management` 目前限 superuser；可建立／編輯帳號、停用、重設密碼與查閱異動紀錄。`templates/sales/user_management.html` 尚無逐畫面授權操作。
- 報表設計 `audience` 只有 admin／所有已登入內部帳號。`sales/reporting/views.py:accessible_report` 另外限制人口分組及原始備註類報表，並非所有 team 報表都可對全員開放。
- 新入口沿用上述清單：每人右側加「畫面權限」，頁首加「權限總覽」。既有帳號、密碼及停用流程保留。

## 2. 方案比較與建議

| 方案 | 管理方式 | 適用情況 |
| --- | --- | --- |
| A 建議先做 | 每人逐畫面勾選，可複製另一位人員的設定，再預覽與確認 | 現有人數少，規則易理解，改動最小 |
| B 擴充版 | 角色範本（例如業務、行政、會計）＋人員例外；明示最終有效權限及來源 | 人數／職務種類增加時；須定義角色繼承及拒絕優先規則 |

本次依後續「請實作人員畫面權限」採 A；實際授權名單仍由 admin 設定，未代為指定。

## 3. 人員權限編輯頁

頁首顯示姓名、帳號、啟用狀態、目前權限版本；管理者不用記帳號才能找到人。

| 區塊 | 操作與顯示 |
| --- | --- |
| 畫面搜尋 | 依名稱找頁面；可只看「已開放」「有變更」 |
| 分類清單 | 戰情首頁、訂單與作業、營運總表、庫存、資料維護、報表中心；實作前逐項核對路由 |
| 每列權限 | 畫面名稱、可查看、可操作、可匯出／系統列印、目前生效狀態 |
| 報表中心 | 展開每份已發布報表，例如總車輛銷售、電動車、油車、性別分析；可逐份授權 |
| 快速複製 | 從另一人複製「畫面權限」到待確認內容，不複製帳號、密碼、superuser 或立即生效 |
| 設定預覽 | 列出將新增／收回的畫面與操作，並顯示該人將看到的選單；不是登入或冒用對方帳號 |
| 儲存確認 | 「確認並套用」後下一次請求生效；未儲存離開前提示 |
| 歷程 | 修改者、受影響人員、時間、前後差異；還原需再次預覽確認 |

未支援某種操作的畫面顯示「不適用」，不能勾選。取消查看時，自動取消相依的操作／匯出並在預覽明示；不暗中保留權限。畫面名稱可調整，底層使用穩定 screen key，不以網址文字或中文標題判斷。

## 4. 最終權限與安全邊界

- 「看不到選單」不等於禁止存取。選單、直接網址、下鑽、分頁、搜尋、CSV／Excel／PDF、HTMX／AJAX 及 API 都要使用同一授權判斷。
- 查看不代表新增、修改、刪除或匯出；操作權限不能藉由直接 POST 繞過。匯出包括完整明細出口，不只是圖表上的按鈕。
- 網頁可查看時，無法可靠禁止瀏覽器自帶列印／截圖；「系統列印」只控制系統提供的列印／PDF 功能，不宣稱阻止複製資料。
- 沒有訂單頁權限的人，報表中「查看原訂單」不顯示，直接開訂單網址仍被阻擋；報表查看權不自動授予訂單維護權。
- 若原本不允許看敏感資料，畫面授權不得擴權。人口資料、原始備註、證件及財務等沿用既有限制；如需開放，另行確認可見欄位與適用人員，不自動放寬。
- 資料範圍（全公司／自己／所屬車行）與畫面權限不同。本期不假裝支援列級資料權限；若需要，另立規格，且首頁數字、搜尋、提示及匯出都要一致過濾。
- admin 的權限管理能力鎖定，不能取消自身維護入口；帳號停用先於所有授權。其他 superuser 不自動等同可修改這份新權限設定，既有帳號管理權限邊界需於實作前明示確認。
- 無權限使用者直接連結得到一致的拒絕結果；不回傳部分資料、筆數或名稱。無任何業務畫面可看時，保留個人密碼、登出與「尚未獲授權」入口。
- 登入後舊分頁不永久保留權限：每次請求重查；每請求內可快取，禁止跨使用者共用授權結果。管理儲存有 CSRF、原子交易及版本檢查，避免兩視窗互相覆寫。

## 5. 資料與程式設計

- `ScreenAccessGrant`：使用者、穩定 screen key、查看／操作／匯出旗標；唯一限制為使用者＋screen key。
- `ReportAccessGrant`：使用者＋既有 `ReportDefinition` 外鍵＋查看／匯出旗標；唯一限制為使用者＋報表。新報表預設不對一般人員開放。
- `UserAccessState`：每位使用者的設定版本、更新時間；`UserAccessRevision` 保存前後快照、操作者與時間。保持稽核，不能經 Django admin 編輯紀錄。
- 共用授權服務與路由白名單：畫面 key 映射可查看、可操作、可匯出的 view／API；URL 巢狀關係不當作權限繼承。測試檢查所有業務路由均已分類，避免新增端點漏管。
- 報表 `audience` 必須與新規則明確銜接：先以現有資格作上限，新設定只縮小；後續若以逐人授權取代 team，需遷移與明示預覽，不能同時有兩套互相矛盾的開放設定。

預計擴充 `sales/views.py` 的帳號管理入口、`sales/urls.py`、`templates/sales/user_management.html`、`templates/base.html`、`config/context_processors.py` 與手機捷徑服務；新增獨立權限服務、表單、模板、模型與 migration；報表讀取與匯出共用服務。Django admin 持續唯讀。

## 6. 遷移、驗收與待確認事項

1. 先唯讀盤點每個畫面／API的現行限制，產生人員與有效權限清單，避免只盤點導覽列。
2. 管理者確認首次授權名單後才啟用；不可自行替所有人開放，也不可突然把現有人員全部鎖住。部署前備份，遷移可重跑，保留上線前對照與回復方案。
3. 驗收矩陣涵蓋 admin、一般人員、停用帳號、無權限帳號；對每個畫面測試 GET、直接 URL、POST、搜尋、下鑽及匯出。
4. 檢查人員甲無法透過修改 ID 取得人員乙／另一報表權限；關閉權限後既有 session 下一次請求遭拒；複製／還原不擴張管理者身分。
5. 桌機、平板、手機與鍵盤可操作；寬表手機改成每個畫面的勾選卡，不依靠橫向大矩陣。

實作採逐人授權，查看與操作／匯出分開；沒有擴大現有敏感報表資格。實際人員名單與可看畫面由 admin 套用確認，此文件不包含任何實際授權決定。
