# 報表分類管理（使用者已選 B，實作規格）

## 入口與權限

資料維護區 → 管理者工具 → 報表分類設定，放在現有「報表設計管理」旁。沿用目前報表管理的 admin 權限，不使用唯讀 Django admin 作正式異動。

目前分類寫在 source_compatibility.py；車型主檔的能源別與 ModelType（煞車／規格）並非本需求的報表車種分類，不混用。

## 方案

| 方案 | 操作方式 | 代價 |
| --- | --- | --- |
| A 最小版 | 類別新增／改名／停用；以原型號清單逐筆或批次指定類別 | 簡單明確，但新型號要手動指定 |
| B 建議版 | 類別管理＋型號規則＋未分類清單；儲存前試算受影響筆數 | 要建立規則驗證、版本及回復機制，開發量較多 |

## B 介面

1. 類別：名稱、顏色、順序、啟用狀態、套用規則數。
2. 型號規則：精確符合／系列開頭、比對文字、目標類別、啟用狀態；不要求使用者輸入 regex。
3. 未分類型號：原型號、目前筆數、對應主檔型號（若有）、批次指定類別。
4. 試算與套用：列出變更前後類別及筆數，確認後發布規則版本；保留修改人、時間與還原入口。

## 防呆

- 保留不可刪除的「其他／待分類」作為未匹配項目；精確型號優先於系列規則，系列衝突須明確處理，不能靜默取第一條。
- 已使用類別不能直接硬刪除，提供停用或移轉；未使用項目才允許刪除。停用前預覽受影響訂單。
- 類別改名維持同一識別碼，避免同名雙群；圖表、下鑽、明細與 CSV 共用同一版本。
- 規則可能重算歷史報表分類，套用前必須明示影響；不改原始訂單、能源、售價、佣金、獎金或收款。
- 實作需要新模型與 migration、唯一限制、transaction、權限／CSRF／稽核、SQLite 與 PostgreSQL 一致性測試。

## B 實作決策

- 使用獨立的單一設定模型與不可覆寫的版本紀錄；草稿／發布分類與規則以嚴格驗證的 JSON 快照存放，沿用 ReportDefinition 的架構。類別與規則使用穩定 UUID／初始識別碼。
- 每次寫入皆驗證版本、transaction、select_for_update 與條件更新；兩個編輯視窗不能互相覆寫。
- 初始規則保持既有精確匹配及 UQ／UC／UG／UT 數字系列、GSX／DS 系列界限；提供精確、文字開頭、接數字系列與接數字／連字號系列，皆不允許自由 regex。
- 精確匹配優先；非精確的重疊規則若指向不同類別須先排除衝突。同類別重疊容許，最長開頭優先。
- 類別停用後其規則不生效，資料歸其他；停用／移轉／刪規則皆須先試算再發布。刪除有目前規則或曾發布規則引用的類別會被阻擋。
- 試算讀取非草稿、非取消訂單，呈現型號、前後分類及影響訂單數；發布時驗證簽章、使用者、草稿版本與試算資料摘要，資料已變則重新試算。
- 每次 HTTP 報表請求固定讀取一份發布快照；分類發布版本納入報表 revision，舊篩選／匯出連結要求重載。
- 還原僅將歷史發布快照複製為新草稿，不立即變更正式報表。類別順序控制管理清單，圖表數值排序仍尊重設計器設定。
- 上線先備份，migration 建立初始等價版本，不回寫訂單或既有報表設計。回退應用程式可保留新增表，必要時使用分類歷史還原。
