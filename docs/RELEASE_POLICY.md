# 正式版號與發布流程

首頁與使用說明均取自 `config/release_notes.py`，不要在模板另寫版號。
自本次發布採 **1.0.0** 基準，舊紀錄只標示已查證的 Git 提交日期。

## 編號規範

依 [SemVer 2.0.0](https://semver.org/lang/zh-TW/) 採 X.Y.Z，不補零：

- PATCH：相容問題修正，例如 1.0.0 → 1.0.1。
- MINOR：相容功能新增／棄用，例如 1.0.1 → 1.1.0。
- MAJOR：不相容變更，例如 1.1.0 → 2.0.0。

相容契約包括文件化 HTTP/整合介面、匯入匯出格式、操作流程與資料保存規則。
一般樣式、文案或不改操作契約的問題修正使用 PATCH，不因改畫面就升 MAJOR。
會讓既有整合或操作失效的變更須明列遷移方式。自動檢查不能取代相容性判斷。
正式歷程只收穩定版，不收 alpha／rc。

## 每次正式發布

1. 在 `RELEASES` 首筆新增版號、預定台北發布日期、標題及分類內容；其餘正式版本不可刪改。
   同日可有多個版本，不以日期自動算版號，也不把每個 commit 當一次發布。
2. 執行 `python scripts/check_release.py`、受影響測試與 migration 檢查，提交並推送。
   CI 從基準提交尋找最新已發布 vX.Y.Z 標籤，驗證歷程不可變、程式／部署異動不得漏升版。
   尚未發布的同一版本可用多次提交修正；首次編版前沒有正式標籤，不偽造比較基準。
3. 完整 CI 通過後，確認仍為預定發布日期，建立附註標籤，例如
   `git tag -a v1.0.0 -m "發布 1.0.0：正式版本歷程"`，執行
   `python scripts/check_release.py --tag v1.0.0`，再 `git push origin v1.0.0`。
4. 核對正式主機工作樹、備份與目標提交，依既有腳本部署，不任意重啟 DB／Redis。
   部署腳本在重建／重啟前強制核對 vX.Y.Z 附註標籤指向目標提交，未標記或不一致即停止。
   部署前後均核對標籤提交、首頁版號、健康與登入後功能。
5. 日期為台北實際發布日期。若未部署且跨日，更新未發布紀錄、重新提交與測試；
   不提前宣稱已發布。已公開版本與標籤不可覆寫或移動，修復須另發新版。

版本隨程式部署，不由公告管理頁修改。12 碼建置雜湊仍負責快取與更新偵測，
不可改成固定版號，避免使用者取得舊靜態資源。

## 編版前紀錄與回復

`LEGACY_UPDATES` 保存經 Git 核對的日期與來源，UI 明列「提交日期」，不是發布日期。
目前整理 2026/09/11–09/14 近期更新，並非宣稱完整歷史。
無 migration；若需回復，使用前一已驗證提交與既有部署流程，保留資料及發布／失敗紀錄，
不刪除訂單或公告、不移動既有標籤。
